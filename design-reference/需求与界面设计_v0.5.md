# 电饭煲预约助手 · 需求设计 & 界面设计 v0.5

> 一句话目标：打开 App，扫一眼列表，找到你要的那个时间，照着左边的数字按电饭煲。全程不需要任何设置。

**v0.5 修订说明**：界面形态沿用已确认的极简列表，落实本轮四点——步进默认 10 分钟并增加自定义输入框；保持向下取整；右侧补「实际完成时间」小字；预期完成时间适度调大但**不与预约时间等大**。全文只写最终形态。

---

## 1. 四点调整，逐个落位

| # | 诉求 | 处理 |
|---|---|---|
| 1 | 步进默认 10 分钟，除预设外可自己输入 | 面板保留 `10 / 15 / 30 / 60` 四个预设，下面加一行「自定义 [输入] 分钟 [使用]」；填完即存、面板收起。合法值 **10–240 的整数分钟**。`20` 这类值走输入框，不再多占一个预设位 |
| 2 | 提前 9 分钟进保温能接受 | **保持向下取整**，不加「取整方向」设置。默认 10 分时最多提前 9 分钟，正是这条规则的结果 |
| 3 | 预期完成时间下面用小字显示实际完成时间 | 右侧时刻下加一行 `实际 07:57 完成`。它把「按 10:20 到底几点煮好」直接写出来，不用用户自己减 |
| 4 | 预期完成时间要不要调到和预约时间一样大 | **不调到一样大，适度调大**：16px → **20px / 字重 600 / 主文字色**。判断理由见 §7 |

数据只多一个可变字段：`{"stepMinutes":10,"targets":[...]}`。步进入口仍是底部说明行末尾一个 11px 灰字链，主界面可见控件仍然只有「+ 添加时间」一个按钮。

## 2. 界面规格（最终形态）

```
┌──────────────────────────────────┐
│  21:37    11月9日 周一            │ ← 实时时钟，无任何按钮
│                                  │
│  现在设为                 煮好时间 │
│  ──────────────────────────────  │
│   9 小时 50 分        07:30 明天  │
│                    实际 07:27 完成│ ← 小字，灰
│  ──────────────────────────────  │
│  10 小时 20 分        08:00 明天  │ ← 20px 主文字色，仍小于左侧
│                    实际 07:57 完成│
│  ──────────────────────────────  │
│  11 小时 50 分        09:30 明天  │
│                    实际 09:27 完成│
│  ──────────────────────────────  │
│      ┌ + 添加时间 ┐               │ ← 唯一按钮
│                                  │
│  预约 = 几小时后煮好，机器自己算开火时间│
│  改动自动保存 · 左滑删除 · 步进 10 分钟 ›│
└──────────────────────────────────┘
```

点「步进 10 分钟 ›」后底部展开（与「添加时间」互斥）：

```
┌──────────────────────────────────┐
│  预约步进 · 一次设定，长期生效     │
│  [10 分] [15 分] [30 分] [60 分]  │ ← 选中态描边
│  自定义   [ 25 ] 分钟   [使用]     │ ← 整数 10–240，填完即存
│  按 25 分钟步进向下取整，只会提前  │
│  煮好并自动保温，绝不迟到；        │
│  提前多久看每行小字。             │
└──────────────────────────────────┘
```

自定义值不在预设里时，面板标题变成「当前 25 分（自定义）」，输入框高亮显示当前值，四个预设都不选中。输入不合法时行内红字提示，不弹窗、不阻断。

### 行的定义

| 位置 | 内容 | 规则 |
|---|---|---|
| 左 | **当前应设的预约时长** | 实时递减、分钟级；27px 橙色，行内最大最亮 |
| 右上 | 预期完成时刻 + 「今天/明天」 | 20px 主文字色，添加时定的，永不自动变 |
| 右下 | **实际完成时刻** | 10.5px 灰字，`N + T`，随步进和当前时间变化 |
| 整行 | 按时刻升序自动排列 | 不用排序、命名、设默认 |

**左边是活的，右边上面是死的、下面也是活的**：靠右上认行（「我要 8 点那行」），靠左边照抄（「按 10:20」），右下用来确认「机器其实 07:57 就好了」。

### 交互仍然只有三个（加一次性的第四个）

| 动作 | 交互 | 保存 |
|---|---|---|
| 看 | 打开即出结果，每分钟更新 | 无需操作 |
| 加 | 点「+ 添加时间」→ 选完即插入并排序 | 自动落盘 |
| 删 | 左滑露出「删除」，点一下即删 | 自动落盘 |
| 设步进 | 首次使用或换机器时点底部小字，选预设或输入自定义 | 自动落盘 |

删到空显示「还没有时间，点下方添加」；重复时刻自动忽略；删错不做二次确认，因为重加只要 2 秒。自动深色、跨天标注、空状态、离线可用都保留且不占控件。

## 3. 计算模型

```
N       = 当前时刻向下取整到分钟（整分钟内数字稳定，每分钟跳一次）
D       = 该行时刻下一次出现：今天剩余 ≥ step 取今天，否则顺延到明天
maxSet  = floor(1440 / step) × step          ← 24 小时内机器能接受的最大值
T       = min( floor((D − N) / step) × step, maxSet )
实际完成 = N + T
显示 T，右上标注「今天/明天」，右下标「实际 HH:MM 完成」
```

- **不减烹饪时长**：客服已确认预约 =「几小时后煮好」，机器自行倒推开火时刻。
- **向下取整**：`N + T ≤ D`，饭只会提前煮好进保温，绝不会晚于右上那个出门时刻。
- **为什么不直接 `floor((D−N)/step)×step`**：当自定义步进不整除 1440（例如 25 分），且今天剩余不足一个步进而顺延到明天后，`D−N` 会略超 24 小时，直接取整可能得到 `1450 分 = 24 小时 10 分` 这种机器按不进去的值。收敛到 `maxSet`（25 分时为 1425 分 = 23 小时 45 分）后，仍可按、仍不迟到，只是提前更多。**右侧「实际完成」小字会如实显示**，不需要任何警示条。
- **提前多久**：步进整除 1440 时（默认 10、15、30、60，以及自定义 20 等），最多提前 `step − 1` 分钟，默认 9 分钟即来自此；不整除时可能再多出 `1440 mod step` 分钟，看右下小字即可。步进越大，提前上限越大，这是自定义值自己的选择。
- **自定义上限 240 分钟**：10 是本机最小步进，240 是为了避免保温过久且保证 `maxSet ≥ step`；覆盖常见机型，改上限只需改一个常量。
- **24 小时上限恒成立**：有 `maxSet` 兜底，`T ≤ 1440` 恒成立，所以依旧不需要上限警示、「建议回来设置时刻」或到点提醒。

### 取整带来的跳变，仍然先讲清楚

目标 08:00、当前 21:37 是「10 小时 20 分 / 实际 07:57」；到 21:41 变成「10 小时 10 分 / 实际 07:51」，数字一下掉 10 分钟。这不是算错——21:41 再按 10:20 就会 08:01 才煮好。右下那行小字正好把这个变化摊开给用户看，比藏起来更可信。

## 4. 数据模型

```json
{
  "version": 5,
  "stepMinutes": 10,
  "targets": ["07:30", "08:00", "09:30"]
}
```

`stepMinutes` 为 10–240 的整数，可以是预设也可以是自定义值。原型会从旧版存储迁移已有的时刻列表**和步进值**，不丢用户加过的时间与设置；旧版步进若不在合法范围则回落到 10。

---

## 5. 明确不做的（以及为什么）

| 不做 | 理由 |
|---|---|
| 取整方向设置 | 会变成第二个需要用户决策的参数。已确认「提前 9 分钟进保温能接受」，默认「宁可提前、绝不迟到」够用 |
| 小于 10 或大于 240 的步进 | 前者本机按不进去，后者保温过久；行内提示拒绝，不弹窗 |
| 设备档案 / 上限 / 输入方式 | 已确认值（几小时后煮好、最大 24 小时、仅倒计时）固化成常量，界面不展示 |
| 24 小时警示 / 回来提醒 | `maxSet` 已兜底，问题不再发生 |
| 烹煮档与「来不及」拦截 | C 不进公式；剩 5 分钟却要煮 30 分钟的饭，需要用户自己判断 |
| 设置后锁定 | 列表是「扫一眼、按完即走」，锁定还得决定锁哪行，成本大于收益。按完若停留页面，数字会继续变 |
| 工作日 / 周末、临时改、跳过今天 | 多个时刻并列，看另一行 / 加一行 / 删一行即可 |
| 保存按钮、确认弹窗、撤销、复制、主题按钮、重置 | 零控件目标 |

两个真实代价不变：**不再校验 `T < C`**、**按完停留时数字仍会变**。都只在边缘场景出现，日常睡前设置不受影响。

## 6. 验收用例

默认 `step = 10`，目标 `07:30 / 08:00 / 09:30`。

| 当前时刻 | 07:30 行 | 08:00 行 | 09:30 行 | 说明 |
|---|---|---|---|---|
| 周一 21:37 | 9 小时 50 分<br>实际 07:27 · 明天 | **10 小时 20 分<br>实际 07:57 · 明天** | 11 小时 50 分<br>实际 09:27 · 明天 | 睡前正常场景，三行都提前 3 分钟 |
| 周二 08:05 | 23 小时 20 分<br>实际 07:25 · 明天 | 23 小时 50 分<br>实际 07:55 · 明天 | **1 小时 20 分<br>实际 09:25 · 今天** | 前两行已过自动顺延，提前 5 分钟 |
| 周三 07:30 | 24 小时<br>实际 07:30 · 明天 | 30 分钟<br>实际 08:00 · 今天 | 2 小时<br>实际 09:30 · 今天 | 07:30 这一分钟已到、剩余不足一个步进 → 顺延，正好 24 小时，提前 0 分钟 |

自定义步进验证：

| 场景 | 结果 |
|---|---|
| 改 `25` 分，周一 21:37 的 08:00 行 | 10 小时整，实际 07:37 完成（提前 23 分钟），四个预设均不选中，面板显示「当前 25 分（自定义）」 |
| 改 `25` 分，07:29 看 07:30 行 | 今天剩余 1 分 < 25 → 顺延；`maxSet = 1425`，得 23 小时 45 分、实际 07:14 完成，**不超 24 小时** |
| 输入 `5` / `300` / `12.5` / 空 | 行内红字「请填 10–240 之间的整数分钟」，原值不变 |

其它：添加 `06:45` 后自动排首行且刷新仍在；左滑删除后刷新不再出现；改步进后所有行立即重算且刷新保持；连续删空显示空状态；20:00 后自动深色。

## 7. 关于第 4 点：我的判断是「调大，但不要一样大」

**不建议和预约时间等大。** 三个理由：

1. **一行只该有一个主角**。这行的任务是「认行 → 抄数」：左边是要执行的值，右边是帮你认行的标签。两串数字等大之后会变成并列对比，用户多一次「该按哪个」的判断；`08:00` 甚至容易被误读成「8 小时」。
2. **活的该比死的重**。左边每分钟在变、且是要按进机器的动作值；右边永远不变，是锚点。视觉权重跟着动作走，锚点抢了主数字的注意力，扫视反而变慢。
3. **但 16px 确实偏小**。睡前、暗光、单手瞄一眼时，右边认行会吃力。所以从 16px 提到 **20px、字重 600、用主文字色**——明显更易读，又仍清楚小于左侧 27px 橙色，橙色只留给「要按的那个数」。

右上把 20px 主信息和 11px 日期放同行，右下再叠一行 10.5px 灰字放实际完成时间，形成「主信息 / 日期 / 实际」三级；信息变多了，层级反而更干净。这是列表类「一个主动作值 + 一个识别标签」场景里比较稳的配法，建议先按这个定稿；真要验证，日后做个等大 A/B 也不迟。

## 8. 视觉规范

无卡片阴影、无渐变、无图标按钮；列表靠细分割线分区。

- 左侧预约值：27px / 700 / 暖橙 `#C4703A` / 等宽数字。
- 右上预期时刻：20px / 600 / 主文字色 / 等宽数字；日期标签 11px 灰字紧跟其后。
- 右下实际完成：10.5px 灰字 / 等宽数字。
- 背景米白 `#FAF7F2` / 深夜 `#171512` 自动切换。
- 「+ 添加时间」全宽虚线低对比；步进入口 11px 灰字加虚下划线；自定义输入框与预设按钮同款圆角。
- 行高 ≥ 82px，左滑热区足够宽，5 行以内不用滚动。

## 9. 待确认（只剩一件小事）

自定义步进范围暂定 **10–240 整数分钟**（默认 10，预设 10/15/30/60），够不够？若以后遇到更大步进的机器，放宽上限只需改一个常量。

其余前几版悬着的问题（工作日分档、焖饭余量、到点提醒、取整方向、提前 9 分钟是否可接受）本轮都已确认或不再需要决策。
